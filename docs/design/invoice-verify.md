# 請求の明細の検証 — 作り直し案（2026-11-04、Fable で検討、#32）

状態: 採用（2026-11-04 夜、鹿内さんが承認）。

## いたちごっこの原因
今の `verify.ts` は「モデルが書いた数字が、モデルが写した引用のどこかで正当化できるか」を正規表現で探している。日本語の言い回しの数だけ抜け道がある開いた問題で、探し方が甘いと通ってしまう。Codex の 18 件はすべてこの構造から出た。

## 推奨: 数はコードが拾い、モデルは対応づけだけ

```
文字起こし（発話ごと #0,#1,…）
 ├ (a) candidates.ts  コードが「言われた数」を全部列挙する（ID 付き）
 │      q1 [#0] 4本 / p1 [#2] 1本330円 / t1 [#5] 合計8800円 / a1 2200円 / u1 「二二十円」(円があるのに読めない) / i1 脱着（料金表の語）
 ├ (b) extract.ts     Opus は行ごとに候補 ID を指すだけ（ID は zod enum をリクエストごとに作る。数字は書かせない）
 ├ (c) resolve.ts     コードが参照を値に戻す。使われない数・二重に使われた数・否定・言い直し・幅 20 秒を検査
 ├ (d) price.ts       料金表で照らす（今の規則を維持）＋金額の検算＋言った合計との照合
 └ (e) 確認事項 → モニター・音声 → 父の答え（同じ候補の文法で読む）→ 承認 → 事務所 PC
```

- 候補の文法の正規化は NFKC・漢数字→算用数字・空白除去だけ。小数点と句読点は消さない。読めない円は必ず確認事項（甘くても安全側に落ちる）。

## 確認事項になる条件
1. 数量の参照が無い
2. 言われた単価・金額がどの行にも使われていない
3. 言われた数量が使われず、同じ発話に同じ単位の使われた数量がある（言い直し）
4. 円があるのに読めない箇所がある（STT の崩れ）
5. 行の節に否定の合図がある（しない・いらない・なし・まいね…）
6. 2 行が同じ語や同じ候補を共有する
7. 1 行の根拠が 20 秒に収まらない（時刻は発話から計算）
8. 品目の語が指した発話に無い
9. 料金表に無い／別名があいまい
10. 発話の単価 ≠ 料金表
11. 単位が料金表と違う
12. 同じ料金表品目の行が 2 つ
13. 数量 × 単価 ≠ 言った金額
14. 言った合計 ≠ 計算した合計
15. 料金表の語が出たのに行になっていない（質問が増えるなら外す）

使わなかった数は質問せず、承認画面に灰色で出す。

## 承認画面
行ごとに 品目・数量・単価とその出所（料金表／発話／答え）・金額・元の発話（品目・数量・単価の箇所を色分け）。下に「使わなかった数」「言った合計 = 計算 ✓」と確認事項。編集はさせず、確認事項が 0 件になるまで承認の言葉は効かない。

## 守るもの・割り切るもの
- 守る: 発話に無い数字が請求に入らない／言った金額が黙って消えない／料金表との食い違いが黙って解決されない／否定・言い直しが黙って通らない。
- 割り切る（父の目が守り。評価で件数を測る）: 同じ発話内で辻褄の合う付け違え（脱着 2 本・バランス 4 本の入れ替え）、STT が数を別の数にきれいに置き換えた場合。
- 脅威モデルは正直なモデルの誤り。悪意あるモデルは想定しない。

## 捨てる・残す
- `verify.ts`: ほぼ捨てる（`kanjiToNumber`・`normalizeNumbers` は `candidates.ts` へ）。
- `schema.ts`: モデルの出力を参照型に。値の付いた行はコードが作る型として残す。
- `extract.ts`: 書き直し。`build.ts`: 順を candidates → extract → resolve → price に。
- `price.ts`・`lookup.ts`: 残す。試験の Codex 18 例は参照の形に直して回帰試験として残す。

## 方言を標準語に変換する層は挟まない
1. 検証は原文との一致で成り立つ。変換すると根拠が変換後の文になり、父が自分の言葉を見られない。変換の誤りが新しい捏造の経路になる。
2. コードが読む数・単位・円は方言の影響が小さい。方言が効く品目の言い方は料金表の別名、否定・文末は合図の語彙表というデータで足りる。
3. Opus は架空の津軽弁で引用を原文のまま扱えた。新設計ではモデルの仕事がさらに軽い。
4. 方言が失われるのは STT の段で、後から変換しても戻らない。
5. 費用と遅れが増える。
語彙表をヒントとして渡すのは可（出力は原文のまま）。調査の結果は `docs/research.md`「方言と用語」。

## 実装のタスク（夜間ループ向け）
- V1 候補の列挙 `candidates.ts`（純粋な関数）
- V2 抽出を候補 ID を指す形に（zod enum を動的に作る）
- V3 参照を値に戻し、保存則・否定・言い直しを確かめる `resolve.ts`（純粋な関数）
- V4 金額の検算・言った合計の照合、通しの順の変更、旧 verify の削除
- V5 承認画面用の表示データ `view.ts`
- V6（任意）訂正の合図があれば言い直しの後の数を自動で採る → 作らない（下の決定 1）
順番: V1・V3 を先（夜間向き）、V2・V4 は次、V5 は画面の前。

## 決めたこと（2026-11-04 夜）
1. 言い直しは必ず聞き返す。訂正の合図があっても後の数を自動では採らない。V6 は作らない。
2. 料金表に無い品目で口で言った値段を使うかは、RacroS III を確かめてから決める（保留、#33）。
3. デモの台詞は「バルブも替えた」のまま撮る。料金表のバルブの単位は「個」に揃え、本数だけを 1 問聞き返す。
